# Carbon Lens — граница интеграции интерфейса

Документ для Backend, Trust, RS и Team Lead. Он фиксирует, что интерфейс `/lens` читает сам, что ждёт
от сервиса, и какие расхождения обнаружены при работе против живого стенда.

Владелец файла: Frontend. Область записи — только `frontend/`.
Состояние контракта: `src/api/generated/openapi.v2.ts` генерируется из `contracts/v2/openapi.v2.yaml`
на ветке `integration/carbon-lens-v2`; `npm run check:api` падает при расхождении. Ручной
`src/lens/types.ts` берёт словари статусов из сгенерированного модуля и больше ничего не объявляет
сам. Раздел 3 описывает стенд PR #15 (`e9817d0`) и оставлен как история; текущее состояние — в 3.1.

## 1. Что интерфейс читает сам, а что получает от сервиса

| Источник | Что берётся | Где в коде |
|---|---|---|
| `data/areas.csv`, `data/areas.geojson` | участки, регион, площадь, годы, `baseline_id`, bbox, контур — для офлайн-каталога | `src/lens/data.ts` |
| `data/sample_requests.geojson` | официальный подучасток `CHECK_TRANSFER_01` и его площадь | `src/lens/data.ts` |
| `data/scenes.csv` | сцены Sentinel-2: дата, облачность, доля пригодных пикселей | `src/lens/data.ts` |
| `data/events.csv` | записи о продуктах гарей: даты, погрешность, число пикселей, ограничения, ссылка | `src/lens/data.ts` |
| `data/methodology/baseline.csv` | базовая линия по годам, включая сценарий до 2029 года | `src/lens/data.ts` |
| `data/methodology/parameters.csv` | CF, 44/12, UNC_allowance, порог H/R, BUF, LK, цены 500/1500/4000 | `src/lens/data.ts` |
| `data/sources.csv` | продукты, версии, лицензии, DOI, атрибуция, ограничения | `src/lens/data.ts` |
| **Сервис** | запас, ΔC, Eproj, базовая линия в CO₂-экв., интервал, R, вычеты, резерв, **Q**, покрытия, зоны, артефакты, паспорт, proof | `src/lens/httpClient.ts` |

Интерфейс **не вычисляет** научные величины. Единственная арифметика на экране: `Q × цена` (цена из
`parameters.csv` или введённая пользователем и помеченная «ваш сценарий») и показ уже полученного
`claim.gap_units`.

## 2. Граница адаптера

```ts
interface LensApiClient {
  kind: 'fixture' | 'http';
  getCatalog(signal?): Promise<Catalog>;
  measureArea(geometry, signal?): Promise<AreaMeasurement>;
  createAnalysis(body, { idempotencyKey, signal?, scenario? }): Promise<AnalysisAccepted>;
  getAnalysis(analysisId, signal?): Promise<Analysis>;          // job_state + result одним ресурсом
  getProof(analysisId, signal?): Promise<Proof>;
  getReport(analysisId, 'json', signal?): Promise<Report>;
  getReportHtml(analysisId, signal?): Promise<string>;
  getArtifact(artifact, signal?): Promise<ArtifactPayload>;     // sha256 проверяется до показа
}
```

Живой клиент — `src/lens/httpClient.ts`, офлайн-набор — `src/lens/fixtureClient.ts`. Экраны не знают,
кто ответил. Режим выбирается конфигурацией: живой сервис по умолчанию, офлайн-набор только по
`?lens=fixture` или `VITE_LENS_API_MODE=fixture`. Автоматической подмены при сбое сервиса нет.

## 3. Расхождения, найденные на живом стенде PR #15 — закрыты

Таблица ниже — исторический след. Она снята в браузере против `backend.serve` на SHA `e9817d0`
(режим CONTRACT_FIXTURE), **до** слияния компонентов в `integration/carbon-lens-v2`. На
интеграционной ветке L1–L6 и L8 закрыты, L7 закрыт иначе, чем предполагалось. Что измерено на
живом стенде сейчас — в разделе 3.1; таблица оставлена, чтобы было видно, чем именно это кончилось.

| № | Наблюдение | Следствие для интерфейса | Что нужно от Backend |
|---|---|---|---|
| L1 | В `Access-Control-Allow-Headers` нет `Authorization`. Запрос с bearer-заголовком не доходит: браузер блокирует preflight | Добавлена схема доступа `demo-header`: `?auth=demo` передаёт токен заголовком `X-Demo-Session`. По умолчанию — bearer, как в roadmap | Разрешить `Authorization` в CORS, тогда `?auth=demo` перестанет быть нужен |
| L2 | Маршрута `POST /areas/measure` нет (404) | Площадь произвольного контура показывается как **предварительная оценка** браузера с явной подписью; предел 2000 га проверяется по ней и перепроверяется сервисом при расчёте | Добавить измерение контура или письменно зафиксировать, что клиент не проверяет предел локально |
| L3 | Маршрутов `POST /auth/login` и `GET /auth/me` нет (404) | Вход в живом режиме: роль выбирается по перечисленным учётным записям, а введённый пароль используется как токен сессии сервиса. В сборку ничего не зашивается, в URL токен не попадает | Опубликовать вход и `/auth/me` с ролями `owner`/`verifier`/`investor` |
| L4 | `evidence.warnings[]` — массив строк (нарушение METHOD FREEZE v1 п.18) | Строка принимается и показывается с кодом `UNSTRUCTURED_WARNING` и серьёзностью `WARNING`; сортировать и подписывать по коду нельзя | Перейти на `{code, severity, message, details}` |
| L5 | `zones[]` пуст, у `Zone` нет `geometry` | Карта не может обвести зону: показывается «зоны не выделены» с объяснением | Либо `Zone.geometry`, либо артефакт `zones` с `zone_id` в properties |
| L6 | `Areas.area_difference_ha` отсутствует (METHOD FREEZE v1 п.17) | Поле показывается только когда приходит; иначе строка скрыта | Добавить знаковую разность |
| L7 | Нулевое заявление возвращается как `SUPPORTED_BY_CASE` (METHOD FREEZE v1 п.12) | Интерфейс показывает статус сервиса и рядом предупреждение, что нулевое заявление не является подтверждённым | Вернуть `NOT_APPLICABLE` + `NO_POSITIVE_CLAIM` |
| L8 | Артефакт `cells` содержит реальную геометрию ячеек и значения по годам | Карточка ячейки CCI построена поверх него; целостность проверяется по sha256 | Сохранить формат; добавить `zone_id` в properties, когда появятся зоны |

Проверено и совпадает: маршруты каталога и анализа, объединение job+result, идемпотентность и 409,
конверт ошибки `{error:{code,message,details}, request_id}`, коды 401/404/422/503, четыре покрытия,
`q=null` против `q=0` с раздельными причинами, неокруглённые R/H/UNC/Radj/B, геодезическая площадь в
результате, отчёт JSON и HTML, proof с `anchor.status = NOT_REQUESTED`, хеш содержания без самого себя.

### 3.1 Состояние на интеграционной ветке

Снято в браузере против `python -m backend.serve` из `integration/carbon-lens-v2`,
`BACKEND_LENS_ENGINE_MODE=REAL`, `BACKEND_LENS_REQUIRE_REAL=1`, участок `RU_TVER_01`, 2019–2024.

| № | Было | Стало |
|---|---|---|
| L1 | `Authorization` не проходил CORS | Проходит: сервис отдаёт `Authorization`, `Content-Type`, `Idempotency-Key` для `GET/POST/PATCH`. Схема `?auth=demo` больше не нужна |
| L2 | `POST /areas/measure` отсутствовал | Есть. Площадь `RU_TVER_01` — `1750.4731237442018` га, подпись на экране «Площадь сервиса». В HTTP-режиме отправка заявки без ответа сервиса отклоняется; браузерная оценка остаётся только в офлайн-режиме |
| L3 | `/auth/login`, `/auth/me` отсутствовали | Есть, плюс `/auth/logout`. Вход по `username` + паролю, роль приходит с сервера, токен живёт в памяти вкладки |
| L4 | `warnings[]` — массив строк | Объекты `{code, severity, message, details}`; строка всё ещё принимается и показывается как `UNSTRUCTURED_WARNING` |
| L5 | `zones[]` пуст, геометрии нет | 20 зон на `RU_TVER_01`, геометрия в артефакте `change_zones`, разрывы наблюдения — отдельным слоем `observation_gap_zones` |
| L6 | нет `area_difference_ha` | Приходит; `coverage_fraction_raw.baseline = 1.0000001134561782` сохранён рядом с клампленой долей |
| L7 | нулевое заявление как `SUPPORTED_BY_CASE` | На живом результате `claim.status = NOT_SUPPORTED_BY_CASE`, `supported_share = 0.0`, `unsupported_gap = 1000.0` при `units.q = 0` и `reason_codes = ["NON_POSITIVE_RELATIVE_RESULT"]` |
| L8 | артефакт ячеек | Без изменений; целостность по `sha256` проверяется до показа |

**Найдено и оставлено как есть (L10).** Сервис присылает `risks[]` (`FIRE`, `FOREST_LOSS`,
`DATA_QUALITY`) и `projection` (горизонт 2029, ряд точек, `q_projection = null`), и оба блока входят
в хеш содержания. Экран их **не показывает**: карточки рисков строятся из зон результата и
официального `data/events.csv`, а ряд проекции — из `data/methodology/baseline.csv`. Оба источника
официальные и подписаны на экране, поэтому это не ошибка в числах, но это два разных ответа на один
вопрос, и при расхождении инвестор увидит не то, что посчитал сервис. Переключение экрана на
серверные блоки — отдельная задача Frontend, не выполнялась здесь.

Сопутствующее исправлено: `AnalysisResult` не объявлял `risks` и `projection` вовсе, хотя контракт
их требует. Теперь объявляет — иначе содержание, которое хешируется, приходилось бы собирать через
приведение типа. Офлайн-набор несёт те же поля с `observed: false` и `status: UNAVAILABLE`: пустой
список читался бы как «рисков не найдено», а искали их там вообще.

**Найдено и исправлено на этой ветке (L9).** Клиентская проверка целостности паспорта не могла
сойтись с сервисом. Сервис считает `sha256(rfc8785.dumps(content_view))` — канонический JSON по
RFC 8785; клиент хешировал `JSON.stringify(view, null, 2)`, и сам `view` не содержал `risks` и
`projection`. Хеш отчёта клиент собирал с `content` в виде **строки**, а сервис — в виде объекта.
Обе проверки поэтому отвергали подлинный паспорт. Не замечалось потому, что офлайн-набор считал свои
хеши тем же неверным способом, то есть обе стороны ошибались одинаково. Исправлено в
`src/lens/passport.ts`: добавлена каноникализация RFC 8785, `contentView` дополнен `risks` и
`projection`, хеш отчёта собирается с объектом. Регрессия закрыта `tests/passportIntegrity.test.ts`
на эталоне живого результата: клиент воспроизводит и `content_hash`, и `report_hash` сервиса.

## 4. Помеченные значения офлайн-режима

`src/lens/fixtures.ts`, одиннадцать наборов: `DOC_EXAMPLE_Q395` (условный пример постановки, Q = 395) и
десять логических векторов — `ZERO_NON_POSITIVE` (S1), `ZERO_UNCERTAINTY`, `ZERO_ROUNDED`,
`UNAVAILABLE_COVERAGE` (S7), `WEAK_OPTICS_VALID_CCI` (S6), `FIRE_SUPPORTED_LOSS` (S2),
`CAUSE_UNKNOWN_LOSS` (S3), `RECOVERY_AFTER_LOSS` (S4), `SUBPLOT_BASELINE` (S5), `UNKNOWN_DRIFT`.
Каждый результат несёт `fixture.label` и `fixture.note`, которые видны на экране. Схематичны и
подписаны: контуры зон и сетка ячеек офлайн-режима.

## 5. Известные ограничения интерфейса

1. Растровые превью, маска облачности и растр гарей в браузер не выдаются; показываются табличные
   метаданные сцен и записи о событиях.
2. **Жизненный цикл заявок в HTTP-режиме принадлежит сервису.** Экран — проекция состояния
   `/requests/...`; `sessionStorage` для заявок в этом режиме не читается и не пишется. Локальный
   цикл остался только у офлайн-режима и помечен на экране. Ни один режим не является реестром
   выпуска единиц.
3. Состояний у заявки пять — `DRAFT`, `SUBMITTED`, `ANALYSING`, `CALCULATED`, `FINALIZED`. Клиент
   отображает их по одному, а состояние, которого он не знает, показывает как «СОСТОЯНИЕ
   НЕИЗВЕСТНО» и закрывает действия над заявкой, вместо того чтобы подставить знакомое.
4. Ограничение доступа по ролям на клиенте — подсказка, а не защита: решение принимает сервис.
   Скрытая кнопка ничего не значит; прямой вызов с чужой сессией получает 403, и это проверяется
   живым тестом, а не предполагается.
5. `401` и `403` разведены по поведению: `403` — отказ в действии, экран продолжает работать;
   `401` завершает сессию и возвращает на вход, потому что дальше не сработает ничего.
6. Путь `/lens` требует SPA-fallback; офлайн-сборка открывается через `index.html#/lens`.
7. Площадь произвольного контура в HTTP-режиме — только серверная; заявка не уходит, пока сервис
   не измерил контур. Браузерная оценка остаётся предварительной подписью на экране.
8. Карточки рисков и ряд проекции строятся из официального `data/`, а не из серверных `risks[]` и
   `projection`, хотя оба блока приходят и входят в хеш содержания. См. L10 в разделе 3.1.
9. Проверка целостности паспорта отвечает на один вопрос: изменилось ли содержимое относительно
   зафиксированного хеша. Совпадение — не подтверждение методики, не право на единицы и не защита
   от повторной продажи.

## 6. Как поднять и проверить

Имена переменных приведены полностью; значений здесь нет и в репозитории их быть не должно.

```powershell
# 1. Сервис. Пароли демо-учётных записей задаются здесь и только здесь.
$env:BACKEND_LENS_DEMO_ACCOUNTS = '1'
$env:BACKEND_LENS_DEMO_PASSWORD_OWNER    = '<свой>'   # не короче 12 символов
$env:BACKEND_LENS_DEMO_PASSWORD_VERIFIER = '<свой>'
$env:BACKEND_LENS_DEMO_PASSWORD_INVESTOR = '<свой>'
$env:BACKEND_DEMO_SESSION      = '<свой, не короче 16>'
$env:BACKEND_LENS_ENGINE_MODE  = 'REAL'
$env:BACKEND_LENS_REQUIRE_REAL = '1'                  # не стартовать, если настоящих движков нет
$env:BACKEND_CORS_ORIGINS      = 'http://127.0.0.1:4173'
.\.venv\Scripts\python.exe -m backend.migrate
.\.venv\Scripts\python.exe -m backend.serve --host 127.0.0.1 --port 8031

# 2. Сборка интерфейса против этого сервиса.
$env:VITE_LENS_API_BASE_URL = 'http://127.0.0.1:8031/api/v2'
npm run build

# 3. Живая проверка в браузере. Учётные данные — только из окружения.
$env:E2E_BASE_URL             = 'http://127.0.0.1:4173'
$env:E2E_LENS_BACKEND_URL     = 'http://127.0.0.1:8031/api/v2'
$env:E2E_LENS_PASSWORD_OWNER    = $env:BACKEND_LENS_DEMO_PASSWORD_OWNER
$env:E2E_LENS_PASSWORD_VERIFIER = $env:BACKEND_LENS_DEMO_PASSWORD_VERIFIER
$env:E2E_LENS_PASSWORD_INVESTOR = $env:BACKEND_LENS_DEMO_PASSWORD_INVESTOR
npx playwright test
```

Без `E2E_LENS_BACKEND_URL` и трёх паролей живой набор пропускается целиком: обычный прогон не
зависит от поднятого сервиса. Офлайн-набор открывается через `?lens=fixture` и помечен на экране;
автоматической подмены при сбое сервиса нет ни в одном режиме.

Playwright — это проверка, а не демонстрация: на показе жюри кликает само, и Playwright не
запускается.
